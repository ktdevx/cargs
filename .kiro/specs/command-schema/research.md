# Research & Design Decisions

## Summary

- **Feature**: `command-schema`
- **Discovery Scope**: New Feature（core-runtime の上に、最初のコマンドライン固有のモジュールを足す）。調査の対象は、既存のコードと規約（`docs/conventions.md`、`docs/ownership.md`、`src/`、`tests/`）、後続のスペックの `brief.md`、および C 標準ライブラリの数値変換の性質である。Web での調査は行っていない。外部のライブラリを採用せず、判断の材料が既存の規約と C 標準の範囲に収まるためである。
- **Key Findings**:
  - 既存の規約は「エラーコードにするのは実行時の失敗だけ」としている。定義の誤り（不正な名前など）は、要件の決定によりエラーコードで返す。名前や選択肢が実行時のデータ（設定やプラグイン）から来る場合があるので、実行時の失敗として扱える。`NULL` の引数や範囲外の添字は、これまでどおり前提条件とする。
  - `CLINE_API` を変数に付けると export の確認が失敗する。組み込みの値型を公開の変数にはできないので、関数が `static const` のオブジェクトへのポインタを返す形にする。変更しない表は `static const` で書いてよい、という規約にも合う。
  - `strtod` は小数点の文字がロケールで変わる。入力の形を自前で検査してから、小数点を現在のロケールの文字に置き換えた複製を `strtod` に渡すと、C 標準ライブラリだけで、ロケールによらない結果を得られる。
  - 読み取りインターフェースを公開 API にすると、公開と内部の 2 系統を持たずに済み、検証が返す定義要素を利用者がそのまま調べられる。

## Research Log

### 既存のコードと規約

- **Context**: 新しいヘッダ、ソース、テスト、エラーコードをどこに置き、どう登録するか。
- **Sources Consulted**: `docs/conventions.md`、`docs/ownership.md`、`include/cline/*.h`、`src/alloc_internal.h`、`src/str.h`、`src/vec.h`、`src/CMakeLists.txt`、`tests/CMakeLists.txt`、`.kiro/specs/core-runtime/design.md`。
- **Findings**:
  - 生成は `cline_error_t cline_<型>_create(…, cline_<型>_t **out)`、破棄は `void cline_<型>_destroy(cline_<型>_t *)`。子を個別に破棄する関数は持たない。
  - 渡された文字列は複製する（`cline_strdup`）。返す文字列は、返したオブジェクトが所有する。
  - 失敗したら、生成したものを受け取る出力先は `NULL`、既存のオブジェクトは呼び出しの前と同じ内容を保つ。
  - エラーコードは `CLINE_ERROR_LIST` の末尾に 1 行ずつ足す。説明文の固有性は既存のテストが確かめる。
  - 内部ヘッダの名前は、同じ名前の公開ヘッダがあれば `src/<名前>_internal.h`、なければ `src/<名前>.h`。
  - `cline_vec_t` は、追加に失敗しても元の内容を保つ。要素は `item_size` バイトの値で、伸長すると要素のアドレスが変わる。
  - 公開ヘッダで `<stdbool.h>` を使っている箇所はまだない。`<stdint.h>` は `src/` で使われている。
- **Implications**:
  - 定義要素のハンドルは、利用者が持ち続けるので、アドレスが変わってはならない。`cline_vec_t` には定義要素そのものではなく、個別に確保した定義要素へのポインタを入れる。
  - build-foundation と core-runtime のファイルで直すのは、追記が前提のもの（`cline.h`、`error.h` の一覧、`src/CMakeLists.txt`、`tests/CMakeLists.txt`、文書）だけである。

### 定義の誤りをエラーコードにすること

- **Context**: `docs/ownership.md` は、呼び出し側のコードを直さない限り必ず起こる誤りを前提条件（`assert`）とし、エラーコードを割り当てないとしている。要件は、不正な名前や名前の衝突をエラーコードで返すと決めた。
- **Sources Consulted**: `docs/ownership.md` の「実行時の失敗とプログラムの誤り」、`requirements.md` の 1.6、2.4、3.4、11.1〜11.5。
- **Findings**:
  - 名前、選択肢、既定値は文字列であり、定数とは限らない。設定ファイルやプラグインの一覧から定義を組み立てるプログラムでは、誤りは実行時にしか分からない。
  - 利用者定義の値型の変換関数が既定値を拒むかどうかは、ライブラリからは実行時にしか分からない。
- **Implications**: 文字列の内容と、定義どうしの関係に由来する誤りはエラーコードにする。`NULL`、範囲外の添字、列挙にない値、ルートでないコマンドの破棄や検証は前提条件にする。この分け方を `docs/ownership.md` に追記する。

### 浮動小数の変換とロケール

- **Context**: 要件 6.7 は、ロケールの設定にかかわらず、小数点として `.` だけを受け付け、同じ入力に同じ結果を返すことを求める。
- **Sources Consulted**: C99 の `strtod`（7.20.1.3）、`localeconv`（7.11.2.1）、`snprintf`（7.19.6.5）についての一般的な知識。今回、規格の本文を取得して確認してはいない。
- **Findings**:
  - `strtod` は、現在のロケールの小数点の文字を使う。`,` のロケールでは `"1.5"` を `1` と読んで止まる。
  - `strtod` は、先頭の空白、`inf`、`nan`、16 進の表記も受け付ける。要件はこれらを拒む。
  - `localeconv` が返す構造体は、後の `setlocale` や `localeconv` の呼び出しで書き換わりうる。
  - `snprintf` で `0.5` を整形すると、現在のロケールの小数点の文字が得られる。`snprintf` は静的な領域を返さない。
  - 10 進の文字列から倍精度への正しい丸めを自前で実装するのは、量が多く、誤りやすい。
- **Implications**: 入力の形（符号、数字、`.`、指数）を自前で検査し、通ったものだけを、小数点を置き換えた複製にして `strtod` に渡す。小数点の文字は `snprintf` で得る。結果が無限大なら失敗とする。`errno` は呼び出しの前の値に戻す。

### 後続のスペックが読み取りに求めるもの

- **Context**: 読み取りインターフェースの範囲と、公開にするかどうかを決める。
- **Sources Consulted**: `.kiro/specs/argv-parser/brief.md`、`.kiro/specs/help-formatter/brief.md`、`.kiro/steering/roadmap.md`。
- **Findings**:
  - argv-parser は、短い名前、長い名前（否定名を含む）、サブコマンド名からの検索と、値型による変換を必要とする。`--name=value` では、名前の部分が NUL で終わっていない。
  - help-formatter は、定義した順の列挙と、表示用の属性、選択肢の一覧を必要とする。
  - 検証の失敗を利用者が調べるには、返された定義要素の名前を読めなければならない。
- **Implications**: 読み取りの関数をすべて公開 API にし、後続のスペックも同じ関数を使う。長い名前の検索は、長さを引数に取る。

## Architecture Pattern Evaluation

| Option | Description | Strengths | Risks / Limitations | Notes |
|--------|-------------|-----------|---------------------|-------|
| 不透明ハンドルの木＋ビルダー関数 | コマンド、オプション、位置引数を個別に確保し、親が子を所有する | ABI を壊さずに属性を足せる。破棄がルート 1 つで済む | 関数の数が多い | `roadmap.md` の決定。採用 |
| 公開構造体の配列 | 利用者が構造体の配列を書いて渡す | 記述が短い | 構造体が ABI になる | `roadmap.md` で却下済み |
| スキーマ用のアリーナ | 1 つの塊から切り出し、破棄でまとめて解放する | 解放が速い | 失敗時に「呼び出しの前と同じ」に戻すのが難しい。core-runtime のユーティリティにない | 不採用 |

## Design Decisions

### Decision: 読み取りインターフェースをすべて公開 API にする

- **Context**: brief は、読み取りを内部向けに必ず用意し、公開の範囲は設計で決めるとしている。
- **Alternatives Considered**:
  1. 内部だけ — 内部ヘッダに宣言し、後続のスペックだけが使う。
  2. 一部を公開 — 名前の取得だけを公開する。
  3. すべて公開 — 公開ヘッダに宣言し、後続のスペックも同じ関数を使う。
- **Selected Approach**: 3。`include/cline/schema.h` と `include/cline/type.h` に宣言する。後続のスペックは、`src/schema_internal.h` を取り込まない。
- **Rationale**: 読み取りの経路が 1 つになる。検証が返す定義要素を、利用者が調べられる。利用者が自分でヘルプや補完を作ることもできる。
- **Trade-offs**: 公開する関数が増え、後から形を変えにくい。関数は足せるが、既存の関数の引数と意味は変えられない。
- **Follow-up**: argv-parser と help-formatter の設計で、足りない読み取りがあれば、このスペックに関数を足す。

### Decision: 値型は「大きさ＋変換関数＋後始末関数」で表し、値は呼び出し側の領域に書く

- **Context**: 組み込みの型と利用者定義の型を同じ仕組みで扱い（7.4）、変換した値の保持を argv-parser に任せる（7.6）。
- **Alternatives Considered**:
  1. 公開のタグ付き共用体で値を返す。
  2. 値型が値の大きさを持ち、変換関数が呼び出し側の領域に書く。
  3. 変換関数が値を確保して、ポインタで返す。
- **Selected Approach**: 2。値型は `value_size` を持つ。変換を求める側が `value_size` バイトの領域を用意し、変換関数がそこに値を書く。組み込みの型の値は、文字列が `const char *`、整数が `int64_t`、浮動小数が `double`、選択肢が `size_t`（一致した選択肢の番号）である。
- **Rationale**: 公開の共用体を ABI にしない。組み込みの型は確保をしない。値の置き場所と寿命を、変換を求める側が決められる。
- **Trade-offs**: 値を `void *` で受け渡すので、型の一致はコンパイラが検査しない。値の型は、値型の種類（`cline_type_kind`）で決まる、という契約で補う。
- **Follow-up**: argv-parser は、型付きの取得関数で値型の種類を確かめる。

### Decision: 変換した値は、入力の文字列を参照してよい

- **Context**: 文字列の値型は、入力と同じ内容の文字列を結果とする（6.2）。複製すると、確保と後始末が要る。
- **Alternatives Considered**:
  1. 文字列の値型が入力を複製し、後始末で解放する。
  2. 値に入力のポインタをそのまま入れ、入力を有効に保つ責任を、変換を求める側に置く。
- **Selected Approach**: 2。「変換した値を使い終えて後始末するまで、変換を求めた側が入力の文字列を有効に保つ」を、値型の契約とする。利用者定義の型も、入力を参照してよい。
- **Rationale**: 文字列の値型が確保をせず、失敗しない。argv の文字列を複製するか借りるかは argv-parser が決めることであり（`docs/ownership.md`）、その決定を妨げない。
- **Trade-offs**: 変換を求める側が、入力の寿命を管理する。
- **Follow-up**: argv-parser の設計で、入力の文字列の寿命を結果オブジェクトの寿命に合わせる。

### Decision: 変換の失敗を表すエラーコード `CLINE_ERROR_INVALID_VALUE` をこのスペックで足す

- **Context**: 変換関数は、失敗を呼び出し元へ伝える。失敗には「入力が不正」と「メモリ確保の失敗」（利用者定義の型）がある。
- **Alternatives Considered**:
  1. 変換関数が真偽値を返す。
  2. 変換関数が `cline_error_t` を返し、入力が不正なときのコードをこのスペックで定める。
- **Selected Approach**: 2。
- **Rationale**: ほかの関数と同じ作法になる。メモリ確保の失敗と、入力の不正を区別できる。値型の契約はこのスペックのものなので、コードもここで足す。
- **Trade-offs**: 解析時のエラーの種類の 1 つを、argv-parser より先にこのスペックが決める。
- **Follow-up**: argv-parser は、このコードを自分の解析エラーの「値の変換の失敗」に対応づける。

### Decision: 組み込みの値型は、関数が返す `static const` のオブジェクトにする

- **Context**: グローバルな登録表に頼らない（6.12）。変更可能なグローバル状態を持たない（10.9）。
- **Alternatives Considered**:
  1. 利用者が毎回 `create` して `destroy` する。
  2. 関数が、ライブラリの中の `static const` のオブジェクトへのポインタを返す。
- **Selected Approach**: 2。文字列、整数、浮動小数に使う。選択肢は一覧を持つので、`create` で生成する。
- **Rationale**: 確保も破棄も要らない。変更しないので、どのスレッドからも使える。
- **Trade-offs**: `cline_type_destroy` は、組み込みの型を渡されたら何もしない、という分岐を持つ。

### Decision: スキーマは値型を借りる

- **Context**: 1 つの値型を複数の定義要素に指定できる（7.7）。値型の所有者と寿命を定める（7.8）。
- **Alternatives Considered**:
  1. スキーマが値型の所有を引き取る。
  2. 参照カウントを持つ。
  3. スキーマは値型を借りる。利用者が、スキーマを破棄した後に値型を破棄する。
- **Selected Approach**: 3。
- **Rationale**: 1 は、同じ値型を 2 つのスキーマで使えない。2 は、値型が変更可能な状態を持ち、別々のスキーマを別々のスレッドで定義するときに同期が要る。3 は `docs/ownership.md` の規則 3（参照されるほうを先に破棄しない）のとおりである。
- **Trade-offs**: 利用者は、生成した値型（選択肢と利用者定義）を持ち続け、破棄の順序を守る。順序の誤りは検出しない。

### Decision: オプションの追加は、種類ごとの関数にする

- **Context**: 値付きオプションだけが値型を取る（2.5）。
- **Alternatives Considered**:
  1. 種類を引数に取る 1 つの関数。値付き以外では値型に `NULL` を渡す。
  2. 種類ごとに 4 つの関数。
- **Selected Approach**: 2。
- **Rationale**: 値付きオプションに値型がない、フラグに値型がある、という定義をコンパイル時に書けなくする。
- **Trade-offs**: 関数が 3 つ増える。

### Decision: 検証の状態はルートに持ち、変更で未検証に戻す

- **Context**: 検証済みのスキーマを変更したら未検証に戻す（8.11）。
- **Alternatives Considered**:
  1. 検証後は凍結し、変更を前提条件の違反とする。
  2. ルートに真偽値を 1 つ持ち、成功した変更のたびに偽にする。
- **Selected Approach**: 2。
- **Rationale**: 要件のとおりである。失敗した変更はスキーマを変えないので、状態も変えない。
- **Trade-offs**: 検証は状態を書くので、同じスキーマの読み取りと同時には呼べない。

## Synthesis

- **Generalization**: 説明文、値の表示名、既定値の設定は、どれも「文字列を複製して、古いものと入れ替える」操作である。内部の関数 1 つ（`cline_schema_replace_string`）にまとめる。名前の重複の検査も、短い名前、長い名前と否定名、サブコマンド名、位置引数名で同じ形だが、比べる対象が違うので、検索の関数を再利用するにとどめる。
- **Build vs. Adopt**: 整数の変換は自前で書く（`strtoll` は先頭の空白を受け付け、桁あふれを `errno` で返す）。浮動小数の変換は、形の検査だけを自前で書き、値の計算は `strtod` に任せる。
- **Simplification**: 読み取りの内部用の層を作らない。検証の結果を保持するオブジェクトを作らず、出力用の引数で返す。スキーマ用のアリーナを作らない。値型に参照カウントを持たせない。

## Risks & Mitigations

- 公開する関数が多く、後から形を変えにくい — 設計の段階で argv-parser と help-formatter の brief に照らして確かめた。足りないものは関数を足して補う。
- 浮動小数の変換が、`,` を小数点とするロケールで誤る — 内部関数のテストで、使えるロケールがあれば切り替えて確かめる。ロケールがない環境では、C ロケールでの確認だけになる。
- 値を `void *` で受け渡すので、領域の大きさや型を誤ると、メモリを壊す — 値型の種類と値の型の対応を、ヘッダのコメントと `docs/schema.md` に書く。検証は `value_size` バイトを確保して変換するので、利用者定義の型の `value_size` の誤りは、検証のテストで見つかりやすい。
- 入れ子の深いスキーマで、破棄と検証の再帰がスタックを使う — 使う量は入れ子の深さに比例する。コマンドラインの入れ子は浅いので、対策はしない。
- 利用者が値型をスキーマより先に破棄する — 検出しない。`docs/schema.md` とヘッダのコメントに順序を書く。
