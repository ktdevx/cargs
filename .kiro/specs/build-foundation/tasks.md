# Implementation Plan

- [x] 1. 土台: リポジトリの骨組みと公開ヘッダ
- [x] 1.1 (P) リポジトリの基本設定とライセンスを置く
  - ビルドディレクトリ、エディタと OS の生成物をバージョン管理から除外する
  - 文字コード（UTF-8）、改行（LF）、末尾の改行、行末の空白の削除、インデント（C と CMake は空白 4 つ、YAML は空白 2 つ）をエディタが自動で適用できる設定を置く
  - テキストファイルの改行を LF にそろえ、Windows でチェックアウトしても変わらないようにする
  - ライセンスの全文（MIT）をリポジトリのルートに置く
  - 完了の目安: ルートにビルドディレクトリを作っても `git status` に現れず、ライセンスの全文がルートで読める
  - _Boundary: RepoFiles_
  - _Requirements: 10.1, 10.3, 10.4_

- [x] 1.2 (P) 公開ヘッダ（バージョン、export の印、入口）を作る
  - メジャー、マイナー、パッチを整数リテラルのマクロとして持ち、最初の値を 0.1.0 にする。3 つを 1 つの数値にまとめるマクロも用意する
  - 公開関数に付ける唯一の印を用意し、「動的ライブラリとして使う」「ライブラリ自身をコンパイルしている」の 2 つの定義の組み合わせと OS・コンパイラに応じて、設計の表のとおりに展開する
  - バージョンを返す関数を、印を先頭に付け、C++ から取り込めるガードで囲んで宣言する
  - 利用者が取り込む唯一の入口のヘッダを置き、ほかの公開ヘッダを取り込むだけにする。公開ヘッダはすべて `argx/` の下に置く
  - 公開する識別子はすべて `argx_` または `ARGX_` で始める
  - 完了の目安: 入口のヘッダだけを取り込む 1 行の C ファイルが、C99・拡張なし・警告ありの設定で、何も定義しない場合と動的ライブラリ用の定義を与えた場合のどちらでも警告なくコンパイルできる
  - _Boundary: VersionSource, ExportMacro, PublicHeaders_
  - _Requirements: 3.5, 4.2, 4.3, 5.1_

- [x] 1.3 公開ヘッダからバージョンを読み取る仕組みを作る
  - 公開ヘッダを文字列として読み、`<major>.<minor>.<patch>` の形で返す。プロジェクト定義より前に呼べるようにする
  - ヘッダがない、3 つのマクロのどれかが見つからない、値が 0〜255 の整数でない場合、ヘッダのパスと見つからなかったマクロ名を示して構成を失敗させる
  - 完了の目安: 単独のスクリプトから呼ぶと正しいヘッダで `0.1.0` が得られ、マクロを 1 つ消したヘッダではパスとマクロ名を含むメッセージで失敗する
  - _Requirements: 5.3, 5.4_

- [x] 2. ライブラリのビルド
- [x] 2.1 トップレベルのプロジェクト定義とオプションを作る
  - CMake 3.21 以上を最初に要求し、古い CMake では必要なバージョンを示して失敗するようにする
  - プロジェクト名を `ArgX` とし、バージョンは公開ヘッダから読んだ値を使う。言語は C だけを有効にする
  - テストのビルド、インストール規則、警告のエラー化の 3 つのオプションを `ARGX_` で始まる名前で用意し、既定をトップレベルなら ON、ほかのプロジェクトに組み込まれたときは OFF にする
  - 静的と動的の切り替えは CMake 標準の変数をそのまま使い、独自の切り替えを作らない
  - コンパイルフラグ、C 標準、出力ディレクトリなどの全体設定を変えない。公開名に `cargs` を使わない
  - 完了の目安: ルートで構成が成功し、プロジェクトのバージョンが公開ヘッダの値と一致する。3 つのオプションがトップレベルでは ON としてキャッシュに現れる
  - _Requirements: 1.2, 1.3, 4.1, 4.4, 6.3, 6.4, 6.5_

- [x] 2.2 バージョンを返す関数とライブラリのターゲットを作る
  - バージョンを返す公開関数を実装する。値は、3 つの要素を 1 つの数値にまとめる内部関数を通して作る。内部関数は内部ヘッダで宣言し、公開の印を付けない
  - ソースの一覧を 1 つの変数で持ち、後続のスペックが 1 行足すだけでソースを追加できるようにする
  - ライブラリの種類を書かずにターゲットを定義し、標準の変数に従って静的または動的になるようにする。成果物の名前は `argx`、Debug 構成では名前の末尾に `d` を付ける
  - インストール後と同じ名前（`ArgX::argx`）の別名を作り、公開ヘッダの取り込みパスをリンクした側へ伝える。内部ヘッダのパスは伝えない
  - 動的のとき、成果物にバージョン全体と ABI バージョン（メジャーが 0 の間は `0.<minor>`、1 以上は `<major>`）を付け、「動的ライブラリとして使う」定義をリンクした側へ伝える。「ライブラリ自身をコンパイルしている」定義は常に内側だけに付ける
  - ほかのライブラリへリンクしない
  - トップレベルの定義からライブラリのディレクトリを追加する
  - 完了の目安: 指定なしの構成で静的ライブラリ、`BUILD_SHARED_LIBS=ON` の構成で動的ライブラリが、ソースを変えずにビルドできる。Debug の成果物名に `d` が付き、Linux の動的ライブラリに `0.1` の SONAME が付く
  - _Requirements: 1.5, 2.1, 2.2, 2.3, 2.4, 2.5, 3.3, 3.4, 4.1, 5.2, 5.3, 5.5, 6.1, 6.2_

- [x] 2.3 共通のコンパイル設定を作り、ライブラリに適用する
  - 指定したターゲットに、C99・標準必須・拡張なしを設定する
  - シンボルの可視性の既定を非公開にし、Windows で全シンボルを export する設定を無効にする。親のプロジェクトが全シンボルの export を有効にしていても、印を付けた関数だけが export されるようにする
  - GCC、Clang、MSVC のそれぞれで警告を有効にする。ライブラリ向けの厳しい警告は指定したときだけ足し、警告のエラー化はオプションが ON のときだけ足す
  - 設定はすべてそのターゲットの内側だけに付け、リンクした側へ伝えない
  - ライブラリのターゲットに、厳しい警告つきで適用する
  - 完了の目安: 詳細表示のビルドで、ライブラリのソースが C99・拡張なし・警告あり・可視性非公開・警告のエラー化つきでコンパイルされ、警告なくビルドが通る。ライブラリにリンクするだけの実行ファイルのコンパイルには、警告と C 標準のフラグが付かない
  - _Requirements: 1.4, 1.6, 3.1, 3.2, 6.6_

- [x] 3. 配布: インストールとパッケージ情報
- [x] 3.1 インストール規則と `find_package` 用のパッケージ情報を作る
  - インストールのオプションが ON のときだけ有効にし、トップレベルの定義から組み込む
  - ライブラリ、公開ヘッダの全体、パッケージ情報を、標準のインストール先の規則に従って配置する。DLL は実行ファイル用の場所へ置く
  - ターゲットを `ArgX::` の名前空間で書き出し、利用者が `ArgX::argx` にリンクするだけで使えるようにする。動的のときだけ「動的ライブラリとして使う」定義が利用者へ伝わるようにする
  - バージョンの互換判定は、メジャーが 0 の間は同じマイナー、1 以上は同じメジャーとする
  - 生成物はインストール先からの相対パスで動くようにし、内部ヘッダ、テスト、Naos、内部関数のテスト用ターゲットをインストールしない
  - 完了の目安: 一時的な場所へインストールすると、ライブラリ、`argx/` の公開ヘッダ、Config・バージョン・ターゲットのファイルが設計の表の場所に置かれ、内部ヘッダが含まれない。静的と動的のどちらでも同じファイル名になる
  - _Requirements: 2.5, 3.3, 3.4, 4.4, 5.3, 7.1, 7.2, 7.3, 7.5, 7.6, 7.7_

- [x] 3.2 pkg-config 用の情報を生成してインストールする
  - 名前を `argx`、バージョンを公開ヘッダの値とし、取り込みパスとリンクのフラグを返すようにする。動的のときだけ「動的ライブラリとして使う」定義をコンパイルのフラグに足す
  - リンクするライブラリ名は、インストールする構成の実際の成果物名にする（Debug では末尾に `d` が付く）。そのため構成ごとに生成する
  - インストール先の場所は、情報ファイル自身の場所からの相対パスで書く。ライブラリのインストール先が絶対パスで指定された場合は絶対パスを書く
  - 完了の目安: インストール後に、インストール先のディレクトリ名を変えてから pkg-config で `argx` を問い合わせると、移動後の場所を指すフラグと `0.1.0` が返る。Debug のインストールでは `-largxd` が返る
  - _Requirements: 2.5, 5.3, 7.1, 7.4, 7.5, 7.7_

- [x] 4. テスト基盤
- [x] 4.1 内部関数のテスト用ターゲットを作る
  - テストのオプションが ON のときだけ作る。ライブラリのターゲットと同じ場所で定義する
  - 動的のときは、同じソース一覧から作る静的ライブラリとし、「動的ライブラリとして使う」定義を付けない。静的のときは、本体にリンクするだけのものとする
  - どちらの場合も、公開ヘッダと内部ヘッダの取り込みパスをリンクした側へ伝え、インストールしない。厳しい警告つきの共通設定は、動的のとき（静的ライブラリとして作る場合）だけ適用する。静的のときはコンパイルするソースを持たないので適用しない
  - 完了の目安: 動的かつテスト ON の構成で、本体の動的ライブラリとは別に静的な内部用ターゲットがビルドされる。テスト OFF の構成ではターゲットが存在しない。インストール物に含まれない
  - _Boundary: Library_
  - _Requirements: 7.6, 8.5_

- [x] 4.2 Naos の取り込みと、テストを 1 行で登録する仕組みを作る
  - テストのオプションが ON のときだけ、Naos をリリースタグ v0.4.0 に固定して自動で取得する。タグの指定は 1 か所だけに書く。OFF のときはこの仕組みを読み込まず、Naos を取得しない
  - トップレベルの定義で、テストが ON のときにテストを有効にしてからテストのディレクトリを追加する
  - 名前とソースを渡すとテストの実行ファイルを作り、共通のコンパイル設定（厳しい警告なし）を適用し、Naos と、公開 API のテストなら構成で選ばれた形のライブラリ、内部関数のテストなら 4.1 のターゲットにリンクする登録関数を用意する
  - Windows で動的ライブラリをビルドするとき、公開 API のテストでは、実行に必要な DLL を実行ファイルの隣へコピーする処理を、Naos によるテストの列挙より前に追加する
  - ファイルに書かれた Naos のテストを CTest に `<name>.<suite>.<test>` の名前と、公開・内部の区別を示すラベルつきで登録する
  - 登録関数の引数が誤っているときは、誤りを示して構成を失敗させる
  - 完了の目安: テストが ON の構成で Naos が取得され、登録関数を呼ぶ仮のテスト 1 つがビルド後に `ctest` で実行される。テストを失敗させると `ctest` が 0 以外で終わる。OFF の構成では Naos の取得もテストの実行ファイルも現れない
  - _Requirements: 8.1, 8.2, 8.3, 8.4, 8.6, 8.8_

- [x] 4.3 バージョンのテスト（公開 API と内部関数）を書く
  - 公開 API のテスト: バージョンを返す関数の値が、ヘッダのまとめた数値と等しいこと。戻り値から取り出したメジャー、マイナー、パッチが、ヘッダの各マクロと等しいこと
  - 内部関数のテスト: 3 つの要素をまとめる内部関数が、ヘッダのまとめるマクロと同じ値を返すこと。境界値（0 と 255）を含める
  - それぞれを決められた手順（公開用と内部用の置き場所、登録の 1 行）で足し、4.2 の仮のテストを置き換える
  - 完了の目安: 静的と動的の両方の構成で、`ctest` が公開 API のテストと内部関数のテストを実行し、すべて通る
  - _Requirements: 5.1, 5.2, 8.4, 8.5, 8.7_

- [x] 4.4 `ctest` に構成が指定されないときの既定を与える
  - `ctest` に構成が指定されなかったとき、既定を Debug にする小さなスクリプトを置く。構成が指定された場合はその指定を優先する
  - トップレベルかつマルチコンフィグのジェネレータのときだけ、トップのディレクトリのテスト設定に登録する
  - この方法は実機で確かめていない。Windows での確認は直後の 4.5 で行う
  - 完了の目安: マルチコンフィグのジェネレータ（手元では Ninja Multi-Config など）で、構成を指定しない `cmake --build` の後、構成を指定しない `ctest` がテストを実行して通る。シングルコンフィグの構成では登録されない
  - _Requirements: 1.1_

- [x] 4.5 追加の引数なしの 3 コマンドを確かめる CI のワークフローを作り、3 つの OS で確かめる
  - ワークフローを新しく作る。すべてのブランチへのプッシュと、プルリクエストの作成・更新で実行する。同じブランチの古い実行は取り消す。権限はリポジトリの読み取りだけにする
  - Linux、macOS、Windows のそれぞれで、構成、ビルド、テストの 3 つのコマンドだけを、追加の引数なしで実行するジョブを置く
  - ブランチをプッシュして実行する。Windows で構成を指定しない `ctest` が動かない場合は、実装で回避せず設計へ戻す（設計が未確認とした点を、ここで早めに確かめる）
  - 完了の目安: プッシュしたブランチで、3 つの OS のジョブがすべて成功する。Windows で、構成を指定しない `ctest` がテストを実行して通る
  - _Requirements: 1.1, 9.1_

- [x] 5. 確認の仕組み
- [x] 5.1 動的ライブラリの export を確かめるチェックを作る
  - 単独で動くスクリプトとして作り、動的ライブラリをビルドしていてテストが有効なとき、CTest に `argx.exports` の名前で登録する
  - export されたシンボルの一覧を、Linux と macOS では `nm`、MSVC では `dumpbin` で得る。道具が見つからなければ失敗させる。macOS では先頭の `_` を取り除いてから比べる
  - 期待する一覧は、公開ヘッダの全体から、コメントを除いたうえで、印の付いた関数宣言の名前を抜き出して作る。手で保守する一覧を持たない
  - export された関数の集合が期待する一覧と完全に一致すること、期待する名前がすべて `argx_` で始まることを確かめ、食い違いがあればその名前を示して失敗させる
  - 完了の目安: 動的の構成で `ctest` が `argx.exports` を実行して通り、export がバージョンを返す関数だけであることが確かめられる。リポジトリのコピーの上で、公開関数の印を一時的に外す、または内部関数に一時的に印を付けると、その名前を示して失敗する（作業ツリーは書き換えない）。静的の構成では登録されない
  - _Boundary: ExportCheck, TestHarness_
  - _Depends: 4.3_
  - _Requirements: 3.1, 3.2, 4.3, 5.5, 9.5_

- [x] 5.2 取り込みを確かめる利用側の小さなプロジェクトを作る
  - 本体のビルドに含めない、リポジトリの外へコピーして使う小さなプロジェクトを作る。取り込み方法を 1 つの変数で `find_package`、pkg-config、`add_subdirectory`、`FetchContent` の 4 つから切り替える
  - 実行ファイルは、バージョンを返す関数の値がヘッダの値と等しければ 0 を返す
  - `find_package` のモードでは、現在のバージョンを要求して見つかること、マイナーの違うバージョンを要求すると見つからないと報告されることも確かめる
  - `add_subdirectory` と `FetchContent` のモードでは、Naos のターゲットとテストが作られていないこと、インストール規則が足されていないことも確かめる。`FetchContent` はネットワークを使わず手元のチェックアウトを指す
  - Windows で動的ライブラリを使うモードでは、利用側が DLL を実行ファイルの隣へコピーする
  - 完了の目安: 手元でインストールした ArgX とリポジトリのチェックアウトを指して、4 つのモードのそれぞれで、利用側のプロジェクトを構成、ビルド、実行でき、実行ファイルが 0 を返す
  - _Boundary: ConsumerCheck_
  - _Depends: 3.1, 3.2_
  - _Requirements: 6.1, 6.2, 6.3, 7.2, 7.3, 7.4, 7.7_

- [x] 5.3 取り込みの確認を通しで実行する駆動スクリプトを作る
  - ビルド済みのビルドディレクトリ、構成、ライブラリの形を受け取り、単独のコマンドで実行できるようにする
  - 一時的な場所へインストールし、インストール先のディレクトリ名を変えてから、移動後の場所を使う
  - 利用側のプロジェクトを作業用のディレクトリへコピーし、4 つのモードを順に構成、ビルド、実行する。作業用のディレクトリは毎回作り直す
  - pkg-config のモードは Linux と macOS だけで実行する。Windows の MSVC では、pkg-config 用のファイルがインストールされていることだけを確かめる
  - 失敗したら、失敗したモードを示して 0 以外で終わる
  - 完了の目安: 手元の静的と動的、Debug と Release の各ビルドディレクトリに対してスクリプトを実行すると、すべてのモードが通って 0 で終わる。利用側の実行ファイルをわざと失敗させると、モード名を示して 0 以外で終わる
  - _Depends: 5.2_
  - _Requirements: 2.5, 7.5, 7.7, 9.4_

## Implementation Notes

- 1.1: `LICENSE` の著作権表示（`Copyright (c) 2026 Kaito Takemura`）はスペックに定めがなく、git の履歴（唯一の人間の作者と最初のコミットの年）から決めた。変更する場合は `LICENSE` の 1 行だけを直す。その後、著作権者は `The ArgX Authors` に変更し、各ソースファイルの先頭にも著作権表示（`Copyright (c) 2026 The ArgX Authors`）と `SPDX-License-Identifier: MIT` を入れた。書き方は `docs/conventions.md` の Procedures にある。
- 1.2: `include/argx/export.h` には `#define ARGX_API __declspec(dllexport)` のような行がある。公開ヘッダから印の付いた宣言を抜き出す処理（5.1）は、プリプロセッサ行を除いてから名前を拾う。
- 1.2: `ARGX_VERSION_NUMBER` は `(unsigned long)` のキャストを含むので `#if` では使えない。`#if` では `ARGX_VERSION_MAJOR` などを個別に使う（6.1 の文書に書く）。
- 1.3: `argx_read_version(<header-path> <out-var>)` は設計より厳しく失敗する。コメントを除いてから読み、同じマクロの二重定義と先頭ゼロ（`010` など）も失敗にする。`version.h` の 3 つのマクロは 1 行ずつ、10 進の 0〜255 で書く。
- 2.1: トップレベルの `CMakeLists.txt` は `CMAKE_MODULE_PATH` を変えず、`include("${CMAKE_CURRENT_LIST_DIR}/cmake/<Module>.cmake")` の形でモジュールを取り込む。後続のタスクも同じ形で足す。バージョンは `PROJECT_VERSION` / `ArgX_VERSION` を参照する。
- 2.2: `src/CMakeLists.txt` の取り込みパスは `BUILD_INTERFACE` だけを持つ。インストール後の取り込みパスは 3.1 が `install(TARGETS ... INCLUDES DESTINATION ${CMAKE_INSTALL_INCLUDEDIR})` で足す。
- 2.2: ライブラリは C 標準ライブラリの関数を呼ばないので、動的ライブラリの `readelf -d` に NEEDED の行が 1 つも出ないことがある（8.1 の依存の確認では、libc 以外がないことを見る）。
- 2.3: `argx_target_defaults(<target> [STRICT])` は、ソースを持たないターゲット（INTERFACE、IMPORTED、ALIAS）、存在しないターゲット、未知の引数を `FATAL_ERROR` にする。`ARGX_WARNINGS_AS_ERRORS` は呼び出した時点の値を読む。MSVC の分岐（`/W4`、`/WX`）は手元で実行できず、CI（4.5、7、8.2）で確かめる。
- 3.1: 互換判定は `SameMinorVersion`（メジャー 0 の間）なので、`find_package(ArgX 0)` や範囲指定は見つからない。メジャーが 0 の間はマイナーまで指定する（6.1、6.2 の文書に書く）。
- 3.1: `CMAKE_INSTALL_LIBDIR=lib64` へ入れた場合、Debian 系の CMake は `CMAKE_PREFIX_PATH` から `lib64/cmake` を探さない。確認には `-DArgX_DIR=<prefix>/lib64/cmake/ArgX` を使う。
- 3.1: 公開ヘッダのインストールは `include/argx` の `*.h` に絞っている。組み込みで `ARGX_INSTALL=ON` を明示すると、`GNUInstallDirs` のキャッシュ変数が親からも見える。
- 3.2: pkg-config が返すフラグは `-I<prefix>/lib/pkgconfig/../../include` の形になる（pkgconf はパスを正規化しない）。5.2、5.3 でフラグを比べるときは、正規化してから比べる。
- 3.2: 設計にない追加として、`argx.pc` を置く前にインストール済みの `argx.pc` を消す `install(CODE "file(REMOVE ...)")` がある。マルチコンフィグで Debug と Release を同じ場所へ入れると、同じ時刻のファイルが「Up-to-date」と扱われて古い `-largxd` が残るためである。同じ場所へ複数の構成を入れた場合、`argx.pc` は最後にインストールした構成のものになる。
- 3.2: `CMAKE_INSTALL_LIBDIR` が絶対パスのとき、`argx.pc` の `prefix` は構成時の `CMAKE_INSTALL_PREFIX` になる。`cmake --install --prefix <別の場所>` で入れると `includedir` がずれ、再配置できない。
- 4.1: `argx_internal` は、動的のとき `libargx_internal.a`（`OUTPUT_NAME` と Debug の `d` なし）、静的のとき INTERFACE ライブラリになる。INTERFACE ライブラリは `cmake --build --target help` に現れないので、存在は `if(TARGET argx_internal)` で確かめる。
- 4.2: 登録関数は `argx_add_test(<name> SOURCES <source>... [INTERNAL])`。`PUBLIC` というキーワードはない（`INTERNAL` がなければ公開 API のテスト）。名前は英数字と下線だけで、全体で一意にする。
- 4.2: Naos v0.4.0 の実物は research.md と 3 点違う。`naos_discover_tests()` に `DISCOVERY_TIMEOUT` と `ALLOW_NO_ASSERTIONS` がある。テストを 1 つも持たない `NAOS_SUITE` はコンパイルエラーになる。実行ファイルをビルドする前の `ctest` には、失敗する `<name>.NOT_BUILT` が 1 つ載る（マルチコンフィグで未ビルドの構成を選んだときも同じ）。
- 4.2: アサーションを 1 つも実行しないテストは、Naos が `no assertion ran` で失敗にする。テストを ON にすると、Naos の `include(GNUInstallDirs)` により `ARGX_INSTALL=OFF` でも `CMAKE_INSTALL_*` のキャッシュ変数が現れる（インストール規則は増えない）。
- 4.2: ほかのビルドディレクトリでは `-DFETCHCONTENT_SOURCE_DIR_NAOS=<取得済みの _deps/naos-src>` を渡すと、ネットワークなしで構成できる。Windows の DLL コピーの分岐は手元で実行できず、CI（4.5、8.2）で確かめる。
- 4.3: テストは公開 5 件（`version.version.*`）と内部 6 件（`version_internal.pack.*`）の計 11 件。設計にない追加として、公開側に `number_has_no_other_bits`、内部側にリテラル（`0x010203UL` など）との比較がある。バージョンが 0.1.0 の間、公開側の `major_` と `patch_` は 0 どうしの比較になる。
- 4.4: `cmake/ArgXCTestDefaults.cmake` は変数 `CTEST_CONFIGURATION_TYPE` が空のときだけ `Debug` を入れる。Naos の生成ファイルも `add_test(NAME ...)` の生成コードもこの変数で分岐するので、`add_test(NAME ... COMMAND ... $<TARGET_FILE:argx>)` の形のテスト（5.1）も `-C` なしで正しい構成で走る。Ninja Multi-Config で確かめた。Visual Studio ジェネレータは 4.5 で確かめる。
- 4.4: 既定は Debug 固定。`CMAKE_CONFIGURATION_TYPES` に Debug がない場合や `CMAKE_DEFAULT_BUILD_TYPE=Release` の場合、`-C` なしの `ctest` は `NOT_BUILT` で失敗する（`-C <構成>` を付ければ通る）。CI のマトリクス（7）では構成を明示する。
- 4.4: テストが OFF のまま `-DFETCHCONTENT_SOURCE_DIR_NAOS=...` を渡すと、CMake が未使用変数の警告を出す（害はない）。
- 4.5: CI の `quickstart` ジョブ（run 43049613386、コミット `a750715`）が Linux、macOS、Windows で成功した。Windows（Visual Studio ジェネレータ、MSVC の `/W4 /WX`）で、構成を指定しない `ctest` が 11 件を実行して通ることを確かめた。`ArgXCTestDefaults.cmake` の方法は実機で確認済み。
- 4.5: ワークフローのアクションはメジャータグで固定している（`actions/checkout@v7`）。設計に固定の方針はない。構成コマンドは要件 1.1 の文字どおり `cmake -S . -B build`。
- 5.1（設計へ戻す点、人の判断が要る）: `argx.exports` は `ARGX_API` を基準にするので、公開関数から印を外した場合は検出できない（その関数は export からも期待する一覧からも消える）。完了の目安の「印を外すと、その名前を示して失敗する」は、設計の規則では満たせない。現状では、印を外すと公開 API のテストが動的の構成でリンクに失敗し（`undefined reference to 'argx_version'`）、ライブラリだけをビルドした場合は `argx.exports` が「公開ヘッダに `ARGX_API` の付いた関数宣言が 1 つもない」で失敗する（名前は出ない。設計にない追加の規則）。公開関数が 2 つ以上になると、印を外した関数は `argx.exports` を通り、その関数を呼ぶ公開 API のテストのリンク失敗だけが検出の手段になる。公開ヘッダの印のない関数宣言を違反にする規則を足すかどうかは、設計の変更として判断する。
- 5.1: 設計にない追加として、export された変数も違反にし（要件 3.2）、ELF のリンカ由来の名前（`_init`、`_fini`、`__bss_start`、`_edata`、`_end`）を無視し、関数宣言でないものに付いた `ARGX_API` を失敗にする。`argx.exports` に CTest のラベルはない（`ctest -L public` などには含まれない）。
- 5.1: 単独実行は `cmake -DARGX_LIBRARY=<動的ライブラリ> -P cmake/ArgXCheckExports.cmake`。関数ポインタを直接返す宣言は名前を誤読するので、`typedef` を使う（6.1 の文書に書く）。`dumpbin` と macOS の `nm -gU` の分岐は偽の出力でしか確かめておらず、CI（7、8.2）で確かめる。
- 5.2: 利用側プロジェクト `tests/consumer/` の入力は、`ARGX_CONSUME_MODE`（`find_package` / `pkg_config` / `add_subdirectory` / `fetch_content`）、インストール済みを使うモードの `CMAKE_PREFIX_PATH`（pkg-config は `PKG_CONFIG_PATH` でもよい）、組み込みのモードの `ARGX_CONSUME_SOURCE_DIR`（チェックアウトのパス。設計に名前の定めはない）。実行ファイルと CTest のテストの名前は `argx_consumer`。組み込みのモードでライブラリの形を選ぶには `-DBUILD_SHARED_LIBS=` を渡す。
- 5.2: 組み込みのモードの確認は設計より厳しい。ArgX のディレクトリに `argx` 以外のターゲットがないこと、`argx` に `-Werror` / `/WX` が付いていないことも見る。後続のスペックが組み込み時にも作るターゲットを足したら、この許可リストを直す。インストール規則はグローバルプロパティ `COMPONENTS`、テストは `TESTS` と `TEST_INCLUDE_FILES`（Naos の列挙はこちらを使う）で検出する。
- 5.2: Windows の DLL コピーと macOS の pkg-config のモードは手元で実行できず、CI（7、8.2）で確かめる。
- 5.3: 駆動スクリプトは `cmake -D ARGX_BUILD_DIR=<dir> -D ARGX_CONFIG=<構成> -D ARGX_SHARED=<ON|OFF> -P tests/consumer/run.cmake`。作業物は `<ARGX_BUILD_DIR>/consumer-check/` に置き、毎回作り直す。1 つのモードが失敗しても残りを実行し、最後に失敗したモードと段階（configure / build / run）を示して 0 以外で終わる。
- 5.3: `CMAKE_BUILD_TYPE` が空のビルドディレクトリ（README の 3 コマンドそのまま）は受け付けない。`-DCMAKE_BUILD_TYPE=<構成>` を付けて構成する。`ARGX_CONFIG` は設計の `<Debug|Release>` より広く、ビルドディレクトリが持つ構成なら受け付ける。`ARGX_SHARED` がビルドの形と合わなければエラーにする。
- 5.3: Windows の判定は「ホストが Windows」（設計は「Windows の MSVC」）。Windows の分岐は `-DCMAKE_HOST_WIN32=1` の模擬でしか確かめておらず、Visual Studio ジェネレータと macOS は CI（7、8.2）で確かめる。同じビルドディレクトリへの並行実行はできない。
