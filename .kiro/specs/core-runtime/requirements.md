# Requirements Document

## Project Description (Input)

出典: `brief.md`（`/kiro-discovery` で作成）

### 誰が困っているか

- **ライブラリの利用者**: 組み込み、アリーナ、メモリ使用量の追跡、確保失敗のテストなどのために、メモリ確保を自分のアロケータに差し替えたい。ライブラリが `malloc` を直接呼ぶと、それができない。
- **利用者とライブラリの開発者**: 失敗の伝え方がスペックごとに違うと、利用者は関数ごとに作法を覚えることになり、開発者は境界をまたぐたびに変換を書くことになる。

### 現状

build-foundation が、ビルド、配布、テスト基盤、命名規約を用意している。メモリ確保とエラー報告の共通の仕組みはまだない。

### 何を変えるか

- 利用者は、確保・再確保・解放の関数と任意のコンテキストを渡して、ライブラリのメモリ確保をすべて差し替えられる。何も渡さなければ標準の `malloc` 系を使う。
- ライブラリのどのコードも、この仕組みを通さずにメモリを確保しない。
- すべての公開関数が、同じ形で成功と失敗を返す。失敗の種類はコードで区別でき、コードから説明文を得られる。
- メモリ確保の失敗は、クラッシュや中断ではなく、エラーとして呼び出し元に返る。
- 誰が確保し誰が解放するかの規約が文書になっていて、後続のスペックが従える。
- 後続のスペックは、確保の失敗を注入できるテスト用のアロケータを使って、失敗時の挙動をテストできる。

### アプローチ

- アロケータは、関数ポインタとコンテキストをまとめた小さな値として、インスタンスごとに渡す。グローバルな設定関数は持たない。
- エラーは、戻り値の状態コードで返す。`errno` も `abort` も使わない。コードの集合は後から足せる形にし、各スペックが自分のコードをどう足すかをここで決める。
- 文字列の複製や伸長する配列など、後続のスペックが共通して必要とする内部ユーティリティは、アロケータの上に用意する。これらは公開しない。

### スコープ

- **含む**:
  - アロケータの公開インターフェース（確保、再確保、解放、利用者のコンテキスト）と、既定のアロケータ
  - ライブラリ内部からアロケータを使うための内部 API
  - 状態コードの型、コードから説明文を得る関数、コードの足し方の規約
  - 所有権と寿命の規約（生成と破棄の対、文字列の扱い、`NULL` の扱い）
  - 内部ユーティリティ（文字列の複製、伸長する配列など、必要最小限）
  - テスト用の失敗注入アロケータ（N 回目の確保を失敗させる、解放漏れを数える）
- **含まない**:
  - コマンドライン固有の概念（オプション、コマンド、argv）
  - 解析エラーの詳細（どの引数で失敗したか）の表現
  - ログ出力、アサーションのフック
  - スレッド同期の仕組み（グローバル状態を持たないことで不要にする）
  - メモリプールやアリーナの実装（利用者が差し替えで持ち込む）
  - スキーマや結果オブジェクトの生成と破棄（command-schema、argv-parser が担当）
  - 利用者向けのエラーメッセージの整形（argv-parser、help-formatter が担当）
  - ビルド設定や export マクロの定義（build-foundation が担当）

### 依存関係

- **上流**: build-foundation（ビルド、命名規約、export マクロ、テストの登録方法）
- **下流**: command-schema、argv-parser、help-formatter。すべてのメモリ確保とエラー報告がここを通る。
- **隣接**: build-foundation（公開ヘッダの置き方に従う）、command-schema（最初の利用者。所有権の規約を実際に適用する）

### 制約

- C99。実行時の依存は C 標準ライブラリのみ。
- 変更可能なグローバル状態を持たない。
- 公開する型は、後からフィールドを足しても ABI を壊さない形にする。アロケータを値で渡す場合は、その構造体の将来の拡張方法を設計で決める。
- 動的ライブラリの境界をまたいで、確保した側と違うアロケータで解放させない。
- 公開名は `roadmap.md` の Naming に従う（ライブラリ名 `clargs`、ヘッダ `<clargs/clargs.h>`、接頭辞 `clargs_` / `CLARGS_`）。
